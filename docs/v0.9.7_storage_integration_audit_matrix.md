# OLRE v0.9.7 Storage Integration Audit Matrix

Date: `2026-05-10`  
Branch: `hardening/storage-integration-and-operational-qa`  
Target Tag: `v0.9.7-storage-integration`

## Purpose

This audit matrix is the operational source of truth for the v0.9.7 storage integration refactor.

It documents:

- where filesystem coupling currently exists
- what storage abstraction should replace it
- which lifecycle category is affected
- how risky the migration is
- what test coverage is expected to move with it

## Architectural Invariant

Raw filesystem operations are allowed only inside:

- `app/storage/*`
- narrowly justified runtime/bootstrap utilities such as `app/runtime.py` and `app/db/sqlite_backup.py`

Raw filesystem operations are not allowed inside:

- `app/services/*`
- `app/web/routes_*`
- `app/batch/*`

Exception policy:

- low-level adapters may remain temporarily only when their behavior is tightly coupled to third-party libraries and a safe storage wrapper does not yet exist
- those exceptions must be explicitly documented and minimized

## Priority Order

1. `app/services/process_batch.py`
2. `app/services/retry_service.py`
3. `app/services/retention_service.py`
4. `app/web/routes_operations.py`
5. `app/batch/qr_debug.py`

## Operational Notes

- `storage_key` must become the preferred identity for retained artifacts
- migration remains compatibility-first: write both, read prefer `storage_key`, fallback legacy path
- cleanup must be treated as high-risk infrastructure with deterministic discovery, validation, and reporting
- processing semantics must remain stable during storage integration

## Out of Scope

The following are intentionally out of scope for v0.9.7:

- storage backend registries
- generic artifact engines
- plugin/provider loading
- blob reference counting
- orphan reconciliation jobs
- distributed storage assumptions
- processing pipeline optimization
